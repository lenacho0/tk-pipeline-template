# TikTok 多维表工作流 - 表6 脚本生成多版本派生规则与输入参数设计

> 更新时间：2026-04-21  
> 适用范围：表6 `脚本执行总表`  
> 目标：解决“如何让脚本生成一次产出多个真正有差异、但仍忠于共性分析和质量约束的版本”，并明确多版本的输入参数、锁定项、变量位、命名规则与落表方式。

---

## 1. 这一步要解决什么

A 阶段已经完成：
- 表结构搭建完成
- 配置表 5 条正式 prompt 已回写
- 质量规则与真源规则已收口

B 阶段不再讨论“脚本怎么生成一条”，而是讨论：
- 一次任务如何生成 N 个脚本版本
- 哪些结构必须锁死，不能飘
- 哪些位置允许变化，且必须产生有效差异
- 多版本如何在表6 中稳定命名、回写、管理状态
- 如何避免多个版本只是换同义词、没有真实测试价值

一句话概括：**把“脚本生成”从单条产出，升级成“受控多版本派生系统”。**

---

## 2. 设计原则

### 2.1 共性优先，变量后置
多版本不是让模型自由发挥，而是在：
- 忠于表2 共性分析结论
- 忠于产品/人物真源
- 忠于 TikTok 转化路径
- 忠于时长与镜头约束
的前提下，只对有限变量位做受控派生。

### 2.2 多版本必须“有测试意义”
多版本之间必须至少在一个核心测试维度上形成明显差异，而不是只换措辞。

### 2.3 锁定结构，放开表达
- 转化骨架锁定
- 功能节点锁定
- 节奏区间锁定
- 真源锁定
- 变量位允许变化

### 2.4 默认少而有效
默认不建议一次生成很多版本。与其 8 个弱差异版本，不如 3 个强差异版本。

我更倾向默认：
- 日常：2-3 个版本
- 明确要做测试：3-4 个版本
- 超过 4 个版本必须有明确测试目的

---

## 3. 表6 的多版本生成本质

表6 的一条记录，不应简单理解为“一个脚本文本”。
更准确地说，它应该是：

**一次脚本生成任务的执行单元。**

这类执行单元有两种模式：
1. 单版本生成
2. 多版本派生生成

因此，表6 需要承接的不只是结果，还要承接：
- 本次生成模式
- 目标版本数
- 派生策略
- 变量控制方式
- 当前版本标识
- 同批次关系

---

## 4. 推荐的生成模式设计

建议为表6 的 `脚本生成模式` 明确收口为 3 类：

### 模式 A：单版本标准生成
适用：
- 首次验证链路
- 用户只要 1 条成片脚本
- 还没进入 A/B 测试阶段

特点：
- 只产出 1 条脚本
- 不做多版本派生
- 仍遵守全部质量规则

### 模式 B：多版本受控派生
适用：
- 同一项目需要输出 2-4 个脚本版本做比对
- 希望测试 hook / 场景入口 / 证据组织 / CTA 方式

特点：
- 共享同一套共性骨架
- 在指定变量位派生多个版本
- 各版本必须有明确“差异标签”

### 模式 C：指定维度定向测试
适用：
- 已经知道这轮只想测一个变量
- 比如只测开场钩子，不想动其他结构

特点：
- 锁定绝大多数结构
- 仅在用户指定测试维度上生成多版本
- 最适合后续规范化 A/B 测试

### 结论
正式系统建议默认使用：
- 默认值：`多版本受控派生`
- 若未填写版本数，则默认 3
- 若未填写测试维度，则系统按推荐维度自动分配

---

## 5. 哪些必须锁死，哪些允许变化

这是 B 阶段最核心的规则。

## 5.1 必须锁死的内容（Hard Lock）

这些内容一旦飘了，多版本就会变成“不同脚本方向”，而不是“同策略下的可测试派生”。

### A. 真源锁定
- 产品外观真源 = 表4
- 人物外貌真源 = 表5
- 不允许版本间更换产品设定
- 不允许版本间更换人物身份底色

### B. 共性骨架锁定
基于表2 共性分析，以下内容必须锁定：
- 推荐复用模式（A/B/C）
- 通用脚本公式主骨架
- 核心传播触发器
- 核心转化机制
- 硬性约束
- timing rules

### C. 转化路径锁定
所有版本都必须覆盖同一条基础转化路径：
- 抓注意力
- 建立兴趣
- 展示产品/解决方案
- 建立信任
- 推动行动

### D. 关键边界锁定
- 平台固定 TikTok
- 单镜头时长规则不变
- 脚本总时长区间不乱飘
- 语言规则由目标市场决定
- 目标市场生活语境规则必须保留

## 5.2 允许变化的内容（Variable Slots）

允许变化，但必须受控。

### 变量位 1：Hook 入口角度
可变内容：
- 痛点直击型
- 反常识/认知冲突型
- 结果前置型
- 场景代入型

说明：
这是最应该优先测试的变量。

### 变量位 2：场景切入方式
可变内容：
- 家庭日常场景切入
- 通勤/出门前场景切入
- 工作/任务场景切入
- 对比型场景切入

说明：
场景可以变，但仍必须服从目标市场本土生活语境，不能脱离产品卖点乱换。

### 变量位 3：产品出场方式
可变内容：
- 早出场
- 中段解决方案式出场
- 对比后出场

说明：
允许测“产品露出节奏”，但不允许把产品藏到不利于转化的位置。

### 变量位 4：信任建立方式
可变内容：
- 个人体验
- 可见细节证据
- 前后对比
- 场景中的自然社会证明

### 变量位 5：CTA 推动方式
可变内容：
- 软 CTA
- 机会损失型 CTA
- 使用结果导向 CTA
- 评论区/链接引导型 CTA

### 变量位 6：口播语气风格
可变内容：
- 朋友分享感
- 轻吐槽感
- 经验建议感
- 快节奏种草感

说明：
语气可以变，但人设不能散。

---

## 6. 不建议允许变化的内容

为了避免版本之间失去可比性，以下内容不建议在同一批派生里同时大幅变化：

- 产品核心卖点主轴
- 主人物身份设定
- 目标市场
- 视频总结构类型
- 镜头数级别差异过大（比如一个 4 镜头，一个 10 镜头）
- 完全不同的 CTA 目标（下单 vs 留言 vs 收藏）

结论：**一次多版本派生，最好只动 1-2 个主变量维度。**

---

## 7. 多版本不是“自由改写”，而是“派生矩阵”

建议把表6 多版本生成逻辑收口成一个“派生矩阵”。

## 7.1 推荐测试维度库
建议系统内置以下测试维度：
- hook_angle
- scene_entry
- product_entry_timing
- trust_builder
- cta_style
- tone_style

## 7.2 推荐默认派生策略

### 策略 S1：单维强差异
- 只测试 1 个变量维度
- 例如只测 hook_angle
- 适合严谨比较

### 策略 S2：双维组合差异
- 测 2 个变量维度
- 例如 hook_angle + scene_entry
- 适合前期探索

### 策略 S3：系统推荐探索
- 由系统根据共性分析自动给出 3 个差异版本
- 每个版本都绑定一个明确主测试点
- 适合用户不想手动设计实验时使用

我建议默认使用 `S3 系统推荐探索`，但每个版本必须明确写出：
- 主测试点
- 次测试点
- 与其他版本的核心差异

---

## 8. 表6 推荐输入参数设计

下面是我建议表6 新增或明确收口的输入参数。

## 8.1 必填/高优先级字段

### 1）脚本生成模式
建议枚举值：
- 单版本标准生成
- 多版本受控派生
- 指定维度定向测试

作用：决定当前任务是单条产出还是派生产出。

### 2）目标版本数
建议类型：数字
建议取值：1-4
默认值：3

规则：
- 单版本标准生成 = 必须为 1
- 多版本受控派生 = 默认 3
- 指定维度定向测试 = 2-4

### 3）测试维度
建议类型：多选或文本枚举
建议值：
- hook_angle
- scene_entry
- product_entry_timing
- trust_builder
- cta_style
- tone_style
- auto

规则：
- 若为空，则默认为 `auto`
- 若模式为“指定维度定向测试”，则不应为空

### 4）版本差异强度
建议枚举值：
- 保守
- 标准
- 激进

含义：
- 保守：版本差异小，适合稳定生产
- 标准：差异清晰，适合常规测试
- 激进：差异更大，但仍不得破坏共性骨架

我建议默认值为：`标准`

### 5）脚本总时长目标
建议类型：数字或区间文本
示例：
- 20
- 25
- 20-25

作用：防止一个版本 18 秒、另一个版本 42 秒，失去可比性。

### 6）目标市场
已有上游可继承，但这里建议在表6 显式展示/回填，用于脚本阶段确认。

---

## 8.2 建议新增的高级字段

### 7）锁定项说明
建议类型：长文本（可程序自动生成）

用途：记录本次派生中哪些内容被锁定。
示例：
- 锁定产品卖点主轴
- 锁定人物身份
- 锁定共性脚本公式
- 锁定转化路径
- 锁定总时长区间

### 8）变量位说明
建议类型：长文本（可程序自动生成）

用途：记录本次允许变化的变量位。
示例：
- 允许变化：hook_angle, cta_style
- 不允许变化：market, product_core_selling_point, model_identity

### 9）派生策略
建议枚举值：
- S1 单维强差异
- S2 双维组合差异
- S3 系统推荐探索

### 10）版本命名规则
建议类型：单选或自动生成
建议默认自动生成，不让用户手填。

### 11）批次ID
建议类型：文本
作用：把同一轮派生生成的多个版本关联成一个批次。

### 12）父任务ID
建议类型：关联/文本
作用：如果后续从某一版本继续派生二次脚本，可追溯来源。

## 9. 表6 推荐结果字段设计

如果表6 既要做“任务表”又要承接“版本结果”，就必须区分“批次级字段”和“版本级字段”。

## 9.1 批次级字段
同一批次的多个版本应共享：
- 项目ID
- 产品ID
- 模特ID
- 目标市场
- 脚本生成模式
- 目标版本数
- 测试维度
- 派生策略
- 锁定项说明
- 变量位说明
- 批次ID

## 9.2 版本级字段
每个版本单独记录：
- 版本编号（V1/V2/V3...）
- 版本名称
- 主测试点
- 次测试点
- 版本差异说明
- 完整脚本 JSON
- 完整脚本文本
- 状态
- 评分/人工选择结果
- 是否选中进入下游

---

## 10. 我建议的落表方式

这里有两个可行方案。

## 方案 A：一版本一行（推荐）

即：
- 同一批次生成 3 个版本
- 表6 中写入 3 行
- 每行对应 1 个版本
- 用 `批次ID` 关联起来

### 优点
- 状态管理简单
- 下游分镜/生图/图生视频天然按版本推进
- 容易筛选“哪个版本入选”
- 容易做失败重跑
- 容易做人工点评与数据分析

### 缺点
- 表面上记录数会变多

但这个缺点我觉得完全可以接受，因为执行型工作流本来就应该一版本一行。

## 方案 B：一批次一行，版本作为子 JSON

### 优点
- 记录数少

### 缺点
- 状态字段难管理
- 下游很别扭
- 单个版本失败不好重跑
- 人工 review 不直观

### 结论
**推荐正式采用：方案 A，一版本一行。**

---

## 11. 推荐命名规则

命名不能只写“版本1/版本2”，否则后续 review 会很痛苦。

建议同时保留三层标识：

### 11.1 批次标识
格式建议：
`SCRIPT-{项目简码}-{日期或流水}`

示例：
- SCRIPT-PJ001-20260421-01

### 11.2 版本编号
- V1
- V2
- V3

### 11.3 版本名称
建议公式：
`{版本编号}-{主测试点}-{简短差异标签}`

示例：
- V1-hook_angle-痛点直击开场
- V2-hook_angle-结果前置开场
- V3-scene_entry-出门前场景切入

这样后续看表，一眼就知道每个版本在测什么。

---

## 12. 如何避免“多个版本只是换词”

这是这一步最重要的防水问题。

建议增加 4 条硬规则：

### 规则 1：每个版本必须有明确主测试点
不允许出现“综合优化版”这种模糊说法。

### 规则 2：每个版本必须写出差异说明
至少说明：
- 本版本主变量位是什么
- 与其他版本相比改变了什么
- 为什么这种变化可能影响转化

### 规则 3：同批次版本的 hook / 场景入口 / 证据组织 / CTA 至少有一个结构层差异
不能只改同义词。

### 规则 4：生成后做一次“版本差异自检”
让模型或程序输出一个差异检查结果：
- 是否共用同一骨架
- 是否确实存在结构性差异
- 是否有版本过于相似
- 是否有版本偏离共性分析

如果差异检查判断：
- 差异不足
- 偏离骨架
则该版本应重生成。

## 13. 推荐的派生执行逻辑

建议执行顺序如下：

### 第一步：先确定批次级锁定骨架
从表2 + 表4 + 表5 + 项目输入中抽出：
- 共性脚本公式
- 核心转化路径
- 目标市场语言和生活语境
- 产品和人物真源
- 总时长范围

### 第二步：确定本轮允许变化的变量位
来源：
- 用户指定
- 或系统自动推荐

### 第三步：为每个版本分配“测试角色”
例如：
- V1 = 痛点直击 hook
- V2 = 结果前置 hook
- V3 = 场景代入 hook

### 第四步：逐版本生成脚本
要求：
- 同骨架
- 同真源
- 同边界
- 不同测试点

### 第五步：执行版本差异自检
输出：
- 批次骨架是否一致
- 版本间差异是否真实成立
- 是否有版本重复/弱差异

### 第六步：落表并进入人工筛选/下游链路

## 15. 推荐默认值（重要）

如果用户不想填很多参数，系统应该也能稳定跑。

建议默认值：
- 脚本生成模式 = 多版本受控派生
- 目标版本数 = 3
- 测试维度 = auto
- 派生策略 = S3 系统推荐探索
- 版本差异强度 = 标准
- 脚本总时长目标 = 跟随表2 共性分析推荐时长 / 或默认 20-25s

系统自动推荐的 3 个版本，建议优先分配为：
1. hook_angle 差异
2. scene_entry 差异
3. trust_builder 或 cta_style 差异

原因很简单：这三个维度最容易形成真实测试价值，同时又不至于把整条脚本结构打散。

## 16. 建议的 prompt 层补充口径

为了支撑多版本派生，表6 的脚本生成 prompt 后续建议补一层“派生约束输入”，但不要改坏现有正式 prompt 主体。

建议额外补充给脚本生成环节的结构化输入包括：
- generation_mode
- target_variant_count
- derivation_strategy
- testing_dimensions
- locked_elements
- variable_slots
- variant_assignment

其中 `variant_assignment` 很关键，例如：
```json
[
  {
    "variant_id": "V1",
    "primary_test": "hook_angle",
    "direction": "痛点直击"
  },
  {
    "variant_id": "V2",
    "primary_test": "hook_angle",
    "direction": "结果前置"
  },
  {
    "variant_id": "V3",
    "primary_test": "scene_entry",
    "direction": "出门前生活场景"
  }
]
```

注意：这不是要推翻现有 prompt，而是在现有 prompt 输入层增加“多版本控制结构”。

## 17. 我建议的最终收口结论

### 最重要的 7 条结论
1. 表6 多版本生成的本质是“受控派生”，不是自由改写。
2. 必须锁定真源、共性骨架、转化路径、目标市场与时长边界。
3. 变量位建议只开放：hook_angle / scene_entry / product_entry_timing / trust_builder / cta_style / tone_style。
4. 单批次最好只动 1-2 个主变量维度。
5. 推荐一版本一行，用 `批次ID` 串联，而不是把多个版本塞进同一行 JSON。
6. 每个版本必须带：主测试点、差异说明、版本名称，不能只叫“版本1”。
7. 必须增加“版本差异自检”，防止多个版本只是换词。

### 推荐默认方案
- 默认模式：多版本受控派生
- 默认版本数：3
- 默认策略：S3 系统推荐探索
- 默认落表：一版本一行
- 默认自动测试维度：hook_angle / scene_entry / trust_builder（或 cta_style）
