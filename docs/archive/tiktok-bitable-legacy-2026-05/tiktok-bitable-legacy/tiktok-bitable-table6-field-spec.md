# TikTok 多维表工作流 - 表6 脚本执行总表字段规格（多版本派生版）

> 更新时间：2026-04-21
> 适用表：表6 `脚本执行总表`
> 目标：把 B 阶段的多版本派生设计收成可直接建表、可直接接程序的字段规格。

---

## 1. 设计目标

表6 不再只是“放一条脚本结果的地方”，而是：

**脚本生成执行表 + 多版本派生承接表 + 下游入口表。**

因此它需要同时满足三件事：
1. 承接上游输入（项目 / 产品 / 模特 / 市场 / 场景参考）
2. 控制本轮脚本生成方式（单版本 / 多版本 / 定向测试）
3. 记录每个脚本版本的执行结果，并为下游分镜/生图/图生视频提供入口

---

## 2. 总体落表原则

### 2.1 一版本一行
正式建议：
- 同一批脚本派生任务生成 3 个版本
- 表6 中创建 3 行记录
- 每行 = 1 个版本
- 通过 `批次ID` 串联同一批次

### 2.2 批次级字段可冗余写到每行
虽然逻辑上存在“批次级信息”，但为了筛选、查看、下游触发简单，允许把批次级字段冗余写到每一行。

这样做的好处是：
- 不需要额外再建“脚本批次表”
- 单行即可看清上下文
- 下游按单行推进最顺

### 2.3 输入字段与系统字段分离
字段需要分成四组：
- A. 上游引用/人工输入字段
- B. 多版本控制字段
- C. 版本结果字段
- D. 运行状态字段

## A. 上游引用 / 人工输入字段

### 1）项目ID
- 字段类型：单行文本 或 关联
- 必填：是
- 来源：上游项目表
- 默认值：无
- 说明：项目主键，用于把脚本版本挂回项目维度
- 建议：如果多维表联动方便，优先用关联；否则文本冗余也可接受

### 2）项目名称
- 字段类型：单行文本
- 必填：否
- 来源：上游项目表同步冗余
- 默认值：自动带入
- 说明：便于人工筛选与查看，不作为强依赖键

### 3）共性分析记录ID
- 字段类型：单行文本 或 关联
- 必填：是
- 来源：表2
- 默认值：无
- 说明：脚本必须明确来自哪条共性分析结论

### 4）产品ID
- 字段类型：单行文本 或 关联
- 必填：是
- 来源：表4
- 默认值：无
- 说明：产品真源定位字段

### 5）产品名称
- 字段类型：单行文本
- 必填：否
- 来源：表4 冗余
- 默认值：自动带入
- 说明：提升可读性

### 6）模特ID
- 字段类型：单行文本 或 关联
- 必填：是
- 来源：表5
- 默认值：无
- 说明：人物真源定位字段

### 7）模特名称
- 字段类型：单行文本
- 必填：否
- 来源：表5 冗余
- 默认值：自动带入
- 说明：提升可读性

### 8）目标市场
- 字段类型：单选
- 必填：是
- 来源：项目表继承，也允许显式回填
- 默认值：继承项目表
- 说明：决定台词语言与场景本土化逻辑
- 建议选项：泰国 / 美国 / 英国 / 印尼 / 菲律宾 / 其他

### 9）场景参考图
- 字段类型：附件
- 必填：否
- 来源：项目表继承展示
- 默认值：空
- 说明：项目级可选场景真源参考

### 10）场景参考说明
- 字段类型：多行文本
- 必填：否
- 来源：项目表继承展示
- 默认值：空
- 说明：补充场景约束，若为空则由脚本阶段自主推导

## B. 多版本控制字段

### 11）脚本生成模式
- 字段类型：单选
- 必填：是
- 来源：人工输入 / 系统默认
- 默认值：多版本受控派生
- 选项：
  - 单版本标准生成
  - 多版本受控派生
  - 指定维度定向测试
- 说明：决定本次任务是单版本还是多版本

### 12）目标版本数
- 字段类型：数字
- 必填：是
- 来源：人工输入 / 系统默认
- 默认值：3
- 约束：1-4
- 说明：
  - 单版本标准生成时必须为 1
  - 其他模式建议 2-4

### 13）测试维度
- 字段类型：多选
- 必填：条件必填
- 来源：人工输入 / 系统默认
- 默认值：auto
- 建议选项：
  - auto
  - hook_angle
  - scene_entry
  - product_entry_timing
  - trust_builder
  - cta_style
  - tone_style
- 规则：
  - 若模式=指定维度定向测试，则不得只有 auto
  - 若模式=多版本受控派生，可允许 auto

### 14）派生策略
- 字段类型：单选
- 必填：是
- 来源：人工输入 / 系统默认
- 默认值：S3 系统推荐探索
- 选项：
  - S1 单维强差异
  - S2 双维组合差异
  - S3 系统推荐探索

### 15）版本差异强度
- 字段类型：单选
- 必填：是
- 来源：人工输入 / 系统默认
- 默认值：标准
- 选项：
  - 保守
  - 标准
  - 激进

### 16）脚本总时长目标
- 字段类型：单行文本
- 必填：否
- 来源：人工输入 / 系统默认
- 默认值：20-25s（若上游无更明确推荐）
- 说明：建议用区间文本，兼容 `20s` / `20-25s`

### 17）锁定项说明
- 字段类型：多行文本
- 必填：是（系统写入）
- 来源：系统生成
- 默认值：无
- 说明：明确本批次不允许变化的内容
- 示例：
  - 锁定产品卖点主轴
  - 锁定模特身份底色
  - 锁定共性脚本公式
  - 锁定目标市场
  - 锁定总时长区间

### 18）变量位说明
- 字段类型：多行文本
- 必填：是（系统写入）
- 来源：系统生成
- 默认值：无
- 说明：明确本批次允许变化的变量位

### 19）共性骨架摘要
- 字段类型：多行文本
- 必填：是（系统写入）
- 来源：系统从表2 摘要抽取
- 默认值：无
- 说明：用于人工快速确认本批脚本基于哪套骨架

### 20）批次ID
- 字段类型：单行文本
- 必填：是
- 来源：系统生成
- 默认值：自动生成
- 说明：同一轮派生任务共享同一批次ID
- 建议格式：`SCRIPT-{项目简码}-{日期流水}`

### 21）父任务ID
- 字段类型：单行文本
- 必填：否
- 来源：系统生成 / 手工指定
- 默认值：空
- 说明：用于二次派生、重做、从已有版本继续扩展时追溯来源

## C. 版本结果字段

### 22）版本编号
- 字段类型：单选 或 单行文本
- 必填：是

### 23）版本名称

- 必填：是
- 来源：系统生成

### 24）主测试点
- 字段类型：单选

- 来源：系统分配 / 人工指定

  - hook_angle
  - scene_entry
  - product_entry_timing

### 25）次测试点
- 字段类型：单选
- 必填：否

### 26）版本差异说明
- 字段类型：多行文本
- 必填：是
- 来源：系统生成
- 默认值：无

### 27）完整脚本JSON
- 字段类型：多行文本
- 必填：是（成功生成后）
- 来源：系统生成
- 默认值：空

### 28）完整脚本文本
- 字段类型：多行文本
- 必填：是（成功生成后）
- 来源：系统生成
- 默认值：空

### 29）脚本摘要
- 字段类型：多行文本

### 33）版本差异自检结果
- 字段类型：多行文本
- 必填：否
- 来源：系统生成
- 默认值：空
- 说明：记录版本差异自检输出
- 最好包含：
  - 是否共用同一骨架
  - 是否存在真实结构差异
  - 是否与其他版本过于相似
  - 是否偏离共性分析

## 6. 字段默认值与系统行为规则

## 6.1 默认值规则
若用户没有明确填写：
- 脚本生成模式 = 多版本受控派生
- 目标版本数 = 3
- 测试维度 = auto
- 派生策略 = S3 系统推荐探索
- 版本差异强度 = 标准
- 脚本总时长目标 = 20-25s 或跟随表2推荐

## 6.2 自动派生规则
若 `测试维度 = auto` 且 `目标版本数 = 3`，推荐自动分配：
- V1：hook_angle
- V2：scene_entry
- V3：trust_builder 或 cta_style

## 6.3 单版本规则
若 `脚本生成模式 = 单版本标准生成`：
- 目标版本数必须改写为 1
- 批次ID 仍生成
- 只创建 1 行
- 主测试点可写 `standard`

## 6.4 定向测试规则
若 `脚本生成模式 = 指定维度定向测试`：
- 测试维度不得为空
- 系统只允许在指定维度内做派生
- 其他变量位默认锁死

## 7. 创建记录逻辑建议

推荐执行逻辑如下：

### 7.1 用户提交任务后
系统先汇总：
- 上游项目/产品/模特/市场信息
- 表2 共性分析信息
- 表6 控制字段

### 7.2 系统先确定派生批次
生成：
- 批次ID
- 锁定项说明
- 变量位说明
- 共性骨架摘要
- 每个版本的主测试点 / 次测试点 / 版本名称

### 7.3 再预创建多条表6记录
例如目标版本数=3，则先建 3 行：
- V1
- V2
- V3

初始状态统一：
- 脚本生成状态 = 待生成
- 下游推进状态 = 未推进
- 是否入选 = 待定

### 7.4 再逐条执行脚本生成
成功则回写：
- 完整脚本JSON
- 完整脚本文本
- 脚本摘要
- 版本差异自检结果
- 状态 = 生成成功

失败则回写：
- 错误信息
- 状态 = 生成失败 / 待重试

## 9. 和现有表结构的关系

这份规格的核心立场是：

- 不新增独立“场景表”
- 不把多版本塞进一个 JSON 大字段里
- 不把表6 做成纯日志表

而是让表6 成为：
- 单版本结果承载单元
- 多版本批次比较入口
- 下游链路的分发入口

这和 2026-04-20 已经定下的架构方向是一致的，没有推翻已有结构，只是把表6 真正做实。
