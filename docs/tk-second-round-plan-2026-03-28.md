# TK 第二轮优化方案（更新版，2026-03-28）

## 先说结论
到今天为止，TK pipeline 已经不再是“能不能跑通”的问题，而是进入了：

1. **能稳定日常运行**
2. **但还不够适合高效批量生产**
3. **主风险已经从单点功能缺失，转向批量调度、错误恢复、吞吐与可运营性**

所以第二轮优化方案要升级。

这次不建议再把重点只放在“某个 prompt 再优化一下”或者“某个阶段单独补丁一下”。
更应该把整条链路往下面四个目标推进：

- **更高成功率**
- **更高批量吞吐**
- **更低人工介入频率**
- **更清晰的生产控制面**

一句话：

> **第二轮不是继续修单点，而是把 TK pipeline 从“能跑的小流水线”推进成“可批量生产的稳定工厂”。**

---

# 一、基于最近进展的最新判断

## 1.1 已经确认稳定下来的部分

### 基础运行层
- dispatcher 已切换到 **Python 3.12 + OpenSSL 3.6.1 + 独立 venv**
- 已脱离此前系统 Python 3.9 + LibreSSL 导致的 Feishu SSL 不稳定问题
- launchd 守护、heartbeat、healthcheck 已形成基本运维闭环

### 主业务链路
- 爆款抓取：可用
- 视频分析：可用
- 产品脚本生成：可用
- 九宫格分镜图生成：可用
- 逐镜头脚本生成：已接通
- 逐镜头图片生成：已接通

### 运维可见性
- dispatcher 有心跳
- 已有每日巡检脚本
- 已有基础运行统计
- 已修复 healthcheck 运行时与日志摘要问题

---

## 1.2 从最近真实日志看到的关键信号

### 信号 A：逐镜头图片链路成功率已经不错
从真实日志看，`逐镜头图片生成` 多次连续成功，说明这条新链路已经具备继续投入的价值。

这意味着：
- 第二轮不该再把它当“实验链路”
- 而应该把它当成正式产能链路来优化

### 信号 B：九宫格分镜图链路仍有结构性失败
历史日志里出现过：
- 模型返回空文本，无法提取 JSON
- retry 后仍失败

这说明九宫格 storyboard 阶段仍有两类问题：
- **模型输出不稳定**
- **失败后的恢复策略还不够细**

### 信号 C：调度器已有统计，但还不够像“生产控制台”
现在日志里已经能看到：
- launched
- success
- failed
- retried
- timeouts

这是好事，但还差一步：
- **现在是“有日志统计”**
- 还不是“能指导批量生产决策的指标系统”

比如目前还看不清：
- 哪个阶段最卡吞吐
- 哪类任务最容易失败
- 哪些失败值得自动重试，哪些应该直接死信
- 当前系统到底更适合跑小批、还是已经能跑中批量

### 信号 D：真正的瓶颈开始从“功能”转向“编排”
现在最需要优化的已经不是单个脚本能否输出，而是：
- 任务如何批量进入
- 哪些环节并发该高，哪些必须保守
- 怎样避免坏样本拖垮整批
- 怎样降低 Feishu 表驱动下的重复扫描、重复写回、重复抢任务成本

这就是典型的“从 demo 流程进入生产流程”的分水岭。

# 二、更新后的第二轮目标

第二轮现在建议明确为 5 个目标：

## 目标 1：提高整链成功率
重点不是某一段单点成功，而是：
- 单条任务端到端成功率提升
- 批量任务整体成功率提升
- 失败后可自动恢复比例提升

## 目标 2：支持批量生产
这里的“支持批量”不是说能一次性扫更多表记录而已，而是：
- 能承受批量待处理任务进入
- 能按阶段限流
- 能让坏样本不拖累整批
- 能优先把高价值任务先跑完

## 目标 3：让调度器更像生产编排层
当前 dispatcher 已经具备雏形，但还不够“编排器”。
第二轮要把它强化成：
- 有阶段并发策略
- 有失败策略
- 有任务优先级
- 有批量处理意识
- 有更清晰状态机

## 目标 4：降低 Feishu 作为真相源带来的调度成本
现阶段不急着立刻大迁移，但必须开始降低它的副作用：
- 重复扫描成本
- 高频读表成本
- 状态写回耦合
- 失败后不易恢复

## 目标 5：为后续“半任务系统化”铺路
这轮不一定完整上 SQLite 驱动全链路，但至少要把数据结构、状态机、错误分类、artifact 组织方式先统一起来。

---

# 三、最新建议：第二轮优化的正确优先级

我建议把第二轮拆成下面 6 个模块，优先顺序也一起定死。

---

# 模块 A：批量生产导向的调度器升级（P0，最高优先级）

这是这轮最该优先做的，不是可选项。

## A1. 分阶段并发控制，正式参数化
现在系统已经有多条链路并行：
- 抓取
- 分析
- 产品脚本
- 九宫格分镜
- 逐镜头脚本
- 逐镜头图片
- 视频生成

它们的资源属性完全不同，不能再用“一个调度器统一轮询 + 自然抢任务”的粗方式长期跑。

### 建议直接落地的并发策略
初始建议值：
- fetch：2~3
- analyze：3~5
- product_script：3~5
- storyboard_grid：2
- shot_script：2~3
- shot_image：3~4
- video_render：1~2
- feishu_writeback：2~3

### 原因
- 文本类任务便宜且快，可以稍高并发
- 九宫格/图像/视频阶段更贵、更慢、更容易受外部模型波动影响，必须保守
- 写回 Feishu 也不能无限打，避免限流或写回抖动

### 目标
让系统从“会并行”变成“知道什么该并行、什么该保守”。

---

## A2. 引入“批次感知”而不是纯扫描感知
现在 Feishu 表驱动模式本质还是：
- 扫描待执行
- 抢任务
- 直接跑

这对于小量任务够用，但对批量生产不够。

### 建议增加批次概念
哪怕先不建完整任务系统，也建议给任务增加最小批次维度：
- batch_id
- batch_source
- batch_priority
- batch_size（可推导）

### 好处
- 可以按批次追踪成功率
- 可以优先跑某个批次
- 可以暂停某批有问题的任务
- 可以在 UI / 表格层更容易做运营管理

这一步不一定要上数据库，但至少要先让 Feishu 侧字段和脚本侧 payload 认得这个概念。

---

## A3. 阶段级限流 + 失败隔离
目标：坏样本别拖死整批。

### 应做
- 每个阶段都有自己的最大并发
- 每个阶段都有自己的最大重试数
- 单任务连续失败后进入“死信/人工复核”，而不是反复抢占执行位
- 同一批次内如果某类错误连续爆发，要能临时熔断该阶段

### 为什么重要
生产里最怕的不是失败，而是：
- 某一类坏任务无限重试
- 把执行位吃满
- 导致正常任务排队饿死

---

# 模块 B：状态机与错误分类升级（P0）

## B1. 全链路统一状态机
现在状态机还偏业务表字段导向，不够工程化。

建议统一最小状态：
- pending
- running
- retry_waiting
- completed
- failed_retryable
- failed_terminal
- dead_letter
- paused

同时保留 stage 维度：
- fetch_trending
- analyze_video
- generate_product_script
- generate_storyboard_grid
- generate_shot_script
- generate_shot_image
- render_video
- sync_result

### 核心原则
- **stage** 表示现在在哪一段
- **status** 表示这段当前生命状态

不要再让单个中文状态字段同时承担两种语义。

---

## B2. 错误分类从“能看日志”升级到“能驱动策略”
原方案里已经提过失败分类，但现在要求更高：

错误分类不是为了好看，而是为了决定：
- 要不要重试
- 是否该切 fallback
- 是否该转人工
- 是否该冻结同类批次

### 建议错误大类
1. `INPUT_MISSING`
2. `UPSTREAM_NETWORK`
3. `UPSTREAM_RATE_LIMIT`
4. `MODEL_EMPTY_OUTPUT`
5. `MODEL_SCHEMA_INVALID`
6. `PROMPT_BUILD_FAILED`
7. `UPLOAD_FAILED`
8. `WRITEBACK_FAILED`
9. `CONFIG_INVALID`
10. `RUNTIME_BUG`
11. `BAD_SAMPLE`

### 决策规则
- `UPSTREAM_NETWORK / RATE_LIMIT / WRITEBACK_FAILED` → 可重试
- `MODEL_EMPTY_OUTPUT` → 限次重试，可换 prompt / fallback
- `MODEL_SCHEMA_INVALID` → 可少量重试，超限转人工
- `CONFIG_INVALID / INPUT_MISSING / PROMPT_BUILD_FAILED` → 直接终止
- `BAD_SAMPLE` → 标记坏样本，跳过
- `RUNTIME_BUG` → 直接打红，进入修复队列

---

# 模块 C：高成功率导向的内容链路优化（P1）

这部分不是不要做，而是优先级排在调度器/状态机之后。

## C1. 九宫格 storyboard 阶段加“双层容错”
因为真实日志已经表明这里有“模型空输出”问题。

### 建议
1. 第一次生成：正常 prompt
2. 若空输出 / JSON 失败：走“压缩版稳态 prompt”重试一次
3. 若仍失败：
   - 标成 `MODEL_EMPTY_OUTPUT` 或 `MODEL_SCHEMA_INVALID`
   - 不继续盲重试

### 目标
减少“同一坏样本反复空转”。

---

## C2. 分析结果质量评分，作为后续生成准入条件
之前方案提过 summary 质量校验，这次要更明确：

### 建议校验项
- 关键字段完整度
- 空值率
- 是否包含明确 hook / 卖点 / 目标人群 / 画面节奏
- 是否只是泛泛总结

### 新规则
- 分析结果质量过低时，不直接进入脚本生成
- 先走“补救分析”或“低优先级队列”

### 原因
垃圾输入直接喂后续，只会把后面的 token、图片、时间一起浪费掉。

---

## C3. 逐镜头链路继续做一致性，但不要过度沉迷 prompt 微调
这部分方向仍然成立：
- 单主角叙事
- 弱化其他人物
- 环境连续性
- 产品/世界观锚点统一

但现在要注意：

> 一致性优化是“锦上添花”，而批量编排、失败恢复、吞吐控制才是“雪中送炭”。

所以它应该是 P1，不是再继续霸占最高优先级。

---

# 模块 D：批量生产能力建设（P1）

## D1. 建立“批量任务输入规范”
现在更像单条记录触发式生产。要支持批量，必须建立一套最小输入规范。

### 批量生产建议最少字段
- batch_id
- product_id / campaign_id
- priority
- expected_output_count
- target_stage
- source_record_ids
- operator_note

### 效果
这样后面才能做：
- 同一产品多脚本批量生成
- 同一脚本多分镜版本生成
- 同一批失败后统一复跑

---

## D2. 支持“批量拆分 + 子任务追踪”
尤其是逐镜头流程，天然适合：
- 母任务
- 子任务
- 子任务 artifacts
- 汇总结果

### 建议至少统一这几个概念
- parent_record_id / parent_task_id
- child_index
- child_type
- artifact_path / artifact_url
- aggregate_status

### 原因
否则批量一大，任务之间就会越来越难追踪。

---

## D3. 增加“低成本批量回归集”
第二轮不能只靠临场跑。

建议固定一组：
- 稳定好样本
- 边界样本
- 坏样本
- 大批量混合样本

作为每次调整后的快速回归池。

这会极大减少“改完一个点，另一个地方 silently 坏掉”的情况。

---

# 模块 E：Feishu 表驱动模式的减负优化（P1）

## E1. 减少全表扫描
如果还继续用 Feishu 直扫直跑，批量一起来成本会很难看。

### 建议
- 优先扫描最近变更窗口
- 能按状态筛就按状态筛
- 能分页增量就不要每轮全表扫
- 将“最近处理过的 record_id + 状态快照”做本地缓存

### 目标
减少：
- API 调用数
- 扫描延迟
- 重复判断成本

---

## E2. 写回从“每次想到就写”优化为“分层写回”
建议把写回分三层：

### 核心字段
写失败视为主流程失败：
- 执行状态
- 关键结果链接
- 错误分类

### 次核心字段
允许延迟写回：
- 统计值
- 参考条数
- 选中的 refs
- 中间信息

### 非关键字段
可异步写回：
- 调试信息
- 额外日志
- 冗余描述

### 作用
降低“主流程明明成功，却因为附加字段写不回而被判失败”的概率。

---

# 模块 F：半任务系统化落地（P2）

我现在的判断是：

- **不建议此刻就大刀阔斧全面迁移**
- **但非常建议开始做“半任务系统化”**

## F1. 先建最小任务事实层
建议最小落地：
- `tasks`
- `task_runs`
- `artifacts`
- `dead_letters`

哪怕先是 SQLite，也值。

## F2. 优先迁入的不是抓取，而是新链路
建议优先顺序：
1. 逐镜头图片生成
2. 逐镜头脚本生成
3. 九宫格分镜生成
4. 分析
5. 抓取

### 原因
- 新链路天然有母子任务结构
- 更适合任务化
- 对批量生产帮助更直接

# 四、更新后的第二轮优先级（最终版）

## P0：现在立刻做
1. **调度器分阶段并发控制参数化**
2. **统一 stage/status 状态机**
3. **统一错误分类，并让错误分类真正驱动重试/终止策略**
4. **九宫格 storyboard 的空输出 / JSON 失败容错机制**
5. **坏任务隔离：死信、暂停、熔断机制**

## P1：紧接着做
6. **分析结果质量评分与准入机制**
7. **批量任务输入规范（batch_id / priority / source list）**
8. **逐镜头母子任务追踪结构**

10. **分层写回机制**
11. **逐镜头一致性继续增强（但降级为 P1）**

## P2：随后推进
12. **SQLite 最小任务事实层**
13. **逐镜头图片链路优先迁入任务化运行**
14. **任务回归样本池建设**
15. **生产指标面板化 / 周报化**

# 五、我对“支持批量生产”的具体定义

为了避免空话，这里把“支持批量生产”定义清楚。

如果第二轮做完，至少应该达到：

## 批量生产最低标准
- 一次进入 20~50 条任务时，不会明显混乱
- 坏样本不会反复吃掉执行位
- 可以看出每个阶段的吞吐与失败分布
- 同一产品 / 同一批次可追踪
- 失败任务可按类别集中复跑
- 人工介入只需要处理“真正异常”，而不是盯全程

## 不算真正支持批量的情况
下面这些都不算：
- 只是表里能同时挂很多待执行记录
- 只是 dispatcher 会一直扫
- 只是失败了之后人工一条条点修复
- 只是日志里能看到很多成功

真正的批量生产，核心是：

> **系统自己知道如何高效地吞任务、隔离坏任务、优先保住主产能。**

# 六、推荐落地顺序（实操版）

## 第 1 步：先做调度器参数化
先把每个阶段的：
- max_concurrency
- retry_limit
- backoff_seconds
- circuit_break_threshold

收进统一配置。

## 第 2 步：补统一错误码与状态机
让每个脚本输出都尽量归一到：
- stage
- status
- error_code
- retryable
- artifact

## 第 3 步：先把九宫格 storyboard 的失败恢复做细
因为它是真实暴露过问题、且会影响后续的一段。

## 第 4 步：补批量字段与母子任务字段
先在 Feishu / payload 层具备批量生产语义。

## 第 5 步：做 Feishu 减负
扫描缓存、增量扫描、分层写回。

## 第 6 步：再推进半任务系统化
尤其优先接逐镜头图片链路。

---

# 七、一句话总纲

**2026-03-28 版第二轮优化，不再以“单点功能补强”为主，而是转向“以批量生产为目标的编排层升级”。**

核心抓手是四件事：

1. **调度器分阶段并发 + 失败隔离**
2. **统一状态机 + 错误分类驱动策略**
3. **批量任务语义 + 母子任务追踪**
4. **降低 Feishu 表驱动模式的扫描与写回成本**

如果这四件事做好，TK pipeline 才会真正从“能跑”进入“能批量稳定产出”。
