# TK Pipeline Lessons Learned

## 1. 先确认真实执行入口

在多套脚本目录并存时（如 `scripts/` 与 `tk_toolkit/`），任何线上改动前都必须先确认：
- 谁在消费任务
- 哪个 dispatcher 在跑
- 它调用的是哪份脚本

否则会出现：
- 明明改了代码
- 线上任务还是按旧逻辑跑
- 误以为修复无效

## 2. 不要让老进程和新进程并行抢任务

必须保证同一时刻只有一套 dispatcher 在消费飞书任务。
否则会导致：
- 任务状态混乱
- 验证结论失真
- 旧逻辑污染新验证

## 3. 真实验证比静态分析更重要

很多关键问题只能在真实任务里暴露：
- FastMoss API code=1002
- 分析任务本地视频依赖
- 脚本生成字段名不存在
- 坏掉的 symlink 占用视频目录路径

## 4. 核心字段 / 可选字段分层

飞书写回必须分层：
- 核心字段：写不进就算主链失败
- 可选字段：写不进只打 warning，不能拖垮主流程

## 5. 脚本生成应走“筛选 → 提纯 → 生成”

不要直接把所有成功分析文本粗暴塞进 prompt。
应该：
1. 先筛出高相关爆款参考
2. 做结构化提纯
3. 生成适配当前产品的脚本

## 6. 分析任务要支持自愈式补拉视频

分析环节不能只依赖本地视频文件。
优先顺序应为：
1. 本地缓存
2. 飞书附件
3. 视频链接补拉

## 7. 目录路径要防坏链

对关键目录（如 `tiktok_videos`）要显式检查：
- 是否为目录
- 是否为 symlink
- 是否为坏链

否则非常容易在 `os.makedirs` 时出现迷惑性报错。
