# TK Pipeline Lessons Learned

## 1. 先确认真实执行入口

在多套脚本目录并存时（如 `scripts/` 与 `tk_toolkit/`），任何线上改动前都必须先确认：
- 谁在消费任务
- 哪个 dispatcher 在跑
- 它调用的是哪份脚本

否则会出现：
- 明明改了代码
- 线上任务还是按旧逻辑跑
- 误以为修复无效

## 2. 不要让老进程和新进程并行抢任务

必须保证同一时刻只有一套 dispatcher 在消费飞书任务。
否则会导致：
- 任务状态混乱
- 验证结论失真
- 旧逻辑污染新验证

## 3. 真实验证比静态分析更重要

很多关键问题只能在真实任务里暴露：
- FastMoss API code=1002
- 分析任务本地视频依赖
- 脚本生成字段名不存在
- 坏掉的 symlink 占用视频目录路径

## 4. 核心字段 / 可选字段分层

飞书写回必须分层：
- 核心字段：写不进就算主链失败
- 可选字段：写不进只打 warning，不能拖垮主流程

## 5. 脚本生成应走“筛选 → 提纯 → 生成”

不要直接把所有成功分析文本粗暴塞进 prompt。
应该：
1. 先筛出高相关爆款参考
2. 做结构化提纯
3. 生成适配当前产品的脚本

## 6. 分析任务要支持自愈式补拉视频

分析环节不能只依赖本地视频文件。
优先顺序应为：
1. 本地缓存
2. 飞书附件
3. 视频链接补拉

## 7. 目录路径要防坏链

对关键目录（如 `tiktok_videos`）要显式检查：
- 是否为目录
- 是否为 symlink
- 是否为坏链

否则非常容易在 `os.makedirs` 时出现迷惑性报错。

## 8. 提示词真源必须单一，代码不要偷偷补创意规则

2026-05-28 的 001/002 链路收口里，最大的一类坑来自“配置表 / 用户文档已经是提示词真源，但代码又在运行时追加产品、参考图、时间段或视频方向规则”。

以后改类似功能时：
- 先确认 prompt 真源在哪里：飞书配置表、用户 Markdown 文档，还是代码模板
- 代码层只做结构化解析、代码块剥离、标题剥离这类机械处理
- 不要擅自追加自然语言创意规则；确实需要补规则时，先让用户确认并写回 prompt 真源
- 测试里要断言最终提交给模型的 prompt 没有多余拼接内容

## 9. 不要复用“看起来差不多”的模型拆分配置

`001-故事板图片视频生成表`、`002-首尾帧视频生成表`、`003-脚本文档分镜链路` 的拆分语义不同。2026-05-28 已把旧 `文本拆分生成-Gemini` 拆成：
- `故事板图片提示词拆分-Gemini`：历史项；2026-06-06 删除旧 `004-故事板图片视频生成表` 时已同步移除，不再作为可用运行配置
- `脚本文档结构化拆分-Gemini`：只服务 003
- 002：严格 Markdown 直拆，不再调用 Gemini

后续重新设计故事板生图表或新增类似表时，不要因为字段都叫“提示词拆分”就复用旧配置 key。配置名、表字段、healthcheck、测试和 dispatcher 口径要一起改，避免旧名字残留误导运行判断。

## 10. 表格视图和 dispatcher watch 必须按记录类型强约束

001 表曾出现母任务、Storyboard 分段、空记录在视图和 dispatcher watch 中混在一起的问题，结果是错误阶段捡走错误记录。

以后只要同一张表里同时存在父任务和子任务：
- 必须有明确的 `记录类型` 或等价字段
- 用户视图要按记录类型筛选
- dispatcher watch 也要按记录类型筛选，不能只靠状态字段
- 修复视图时顺手扫描历史脏数据，纠正误标记录和空任务名

## 11. 外部长任务要把 task id 当作恢复锚点

OTU 图片 / 视频任务不是一次函数调用，而是“提交任务 -> 轮询 -> 下载 -> 上传 -> 写回”的长事务。2026-05-28 的首帧图和首尾帧视频都踩过同一个坑：dispatcher 重启、熔断或网络抖动后，本地轮询中断，但上游任务其实已经完成。

以后这类链路默认要做到：
- 提交成功后尽快写回上游 `task_id`
- 记录处于“生成中”且已有 `task_id` 时，优先恢复轮询，不重新提交
- 失败写回不要清空 `task_id`，除非用户明确触发“重新生成”
- dispatcher claim 不得清空任务 ID 或原始响应；重生路径单独负责清空旧任务并递增版本

## 12. 区分上游失败、上游排队、本地写回失败

“任务卡住”不等于代码死循环，也不等于模型没生成。2026-05-28 排查里至少有三种状态：
- 上游返回 `upstream_error / 没有可用token`
- 新任务仍在 `queued`，progress 为 0
- 上游已经 completed，但本机下载 R2 文件或上传飞书失败

以后排障先查上游任务状态和本地日志，再决定是否重试。状态字段和错误信息要尽量写出阶段，例如 `UPSTREAM_COMPLETED_LOCAL_WRITEBACK_FAILED` 这类语义，比笼统写“失败”更能防止重复烧模型。

## 13. 下载和写回是独立风险点，要有重试

R2 `pub-*.r2.dev` 下载 mp4 时出现过 SSL EOF、read timeout；OTU `/v1/videos` 也出现过 524 / SSL / timeout。上游生成成功以后，本地下载、文件校验、飞书上传、字段写回仍可能失败。

以后处理媒体文件时：
- 网络下载要有有限重试和合理 read timeout
- 下载失败不要抹掉上游任务 ID
- 成功下载但上传/写回失败时，要保留本地路径和上游 URL 方便恢复
- 恢复命令优先复用已有 task，不重复提交模型任务

## 14. 参考图不是“传了就一定强约束”

001/008 图片参考曾出现人物和产品跑偏：父任务、产品、模特和环境图都没错，但拆分 prompt 继承了脚本文字里的服装/产品外观，和参考图冲突；另一次根因是 OTU gpt-image-2 图片参考图按旧顶层 `image_base64` / multipart 方式提交，没有走当前接口文档要求的 JSON `metadata.urls`。

以后涉及多参考图时：
- OTU gpt-image-2 图片参考图统一走 `metadata.urls`，本地文件必须转成 `data:image/...;base64,...`
- OTU 图片参考上限按接口文档为 5 张，优先保留产品图、主参考图、模特图，再保留普通参考图
- 不要把 OTU 图片的 JSON `metadata.urls` 和 OTU/Veo/Omni 视频的 multipart `input_reference[]` 混用
- prompt 中明确“参考图优先于脚本文字外观”
- 测试不仅看字段是否传入，还要看最终参考图顺序和主图选择

## 15. 能直拆就不要让模型拆

002 首尾帧表最终收口为严格 Markdown 直拆，原因是模型拆分即使写了“只抽取、不改写”，仍可能压缩、补充、遗漏或改写创意。

以后用户能提供稳定结构时，优先设计机器可解析格式：
- 标题结构固定
- 缺段直接失败并提示修正
- 只提取代码块或标题下正文原文
- 不做 JSON 兜底和自然语言改写

这会让错误更早、更明确，也能保护用户给定 prompt。

## 16. 收口验证要同时查测试、旧口径残留和真实运行入口

2026-05-28 的有效验证组合是：
- 跑相关单测和 `py_compile`
- 用 `rg` 查旧配置名、旧 key、旧环节名是否还残留
- 重启 / kickstart 正在运行的 ryan dispatcher
- 跑 healthcheck，确认显示的是新口径
- 必要时用真实记录 smoke test 或只读查询确认状态

只跑单测不够；这类多维表格 + dispatcher 项目里，最容易翻车的是“代码改了，但配置、视图、watch 或线上进程仍按旧口径运行”。

## 17. 用户入口要极简，运行字段不要暴露成操作面板

2026-05-27 新增 001 故事板视频表和 002 首尾帧表时，都经历了“字段很多、能力很全，但用户入口容易变乱”的问题。后续收口方向证明：用户入口只保留真正需要填写/触发的字段，运行过程字段放到结果视图或排错视图。

以后设计多维表格入口时：
- 用户入口只放任务名、输入内容/附件、必要选择项、一个明确触发状态
- 版本号、task id、原始响应、本地路径、file_token、错误分类等字段不要放在主入口
- 审核/重生/结果/排错拆成独立视图，不把所有动作堆在一个视图里
- 表结构测试要断言入口视图字段顺序和隐藏字段，防止后续越加越乱

## 18. 飞书关联字段写回要写 record id，不要回填 cell 对象

2026-05-27 的故事板子记录曾修正过一次：从母任务继承 `关联产品记录`、`选择模特` 时，不能把飞书读出来的关联 cell 原样写回子记录，而要提取 `record_ids` 列表。

以后处理飞书 Base 字段时：
- 读字段和写字段的数据形态不能假设相同
- relation/link 字段写回优先使用 record id 数组
- 附件字段写回使用附件结构，URL 字段写回使用 URL 字段接受的结构或空值
- 单测要覆盖“从真实读取形态 -> 写回 payload”的转换，不只测业务值

## 19. 清空字段要尊重字段类型，URL 字段用 null 比空字符串稳

2026-05-27 的 `分镜视频URL` 清空从 `""` 改为 `None`，原因是飞书 URL 字段对空字符串不一定等价于清空，可能造成写回失败或残留旧链接。

以后 dispatcher claim 或重生重置字段时：
- 附件字段清空用 `[]`
- 时间字段清空用 `None`
- URL / 日期时间这类 typed 字段优先用 `None`
- 文本状态字段才用 `""` 或明确状态值
- `claim_clear_values` 要支持按字段写入不同类型，不要只有 `claim_clear_fields` 这种粗粒度清空

## 20. 一张表混合父子记录时，重生路径要有版本和废弃语义

2026-05-27 首尾帧表开始支持母任务批量拆场景、场景子任务、各阶段重生和历史记录。这里的坑是：如果只覆盖旧记录，很难判断哪个批次有效；如果不废弃旧子任务，dispatcher 可能继续捡旧任务。

以后类似链路默认要有：
- `记录类型` 区分母任务和子任务
- `记录状态` 区分有效和已废弃
- `批次ID` / `当前批次ID` 标记一轮拆分
- 拆分版本、图片版本、视频版本分别递增
- dispatcher 跳过已废弃记录，并按记录类型跳过不该消费的母任务/子任务

## 21. 外部模型参数不能跨模型照抄

2026-05-27 故事板 Omni 视频接入时，单测明确约束 OTU Omni 走 `/v1/videos` multipart，重复字段 `input_reference[]` 传参考图，并且不传 `seconds`。这和其他 OTU/Veo 图生视频路径并不完全一样。

以后接新模型时：
- 先为该模型写独立 submit 单测，锁住 URL、form 字段、参考图字段名和不该传的参数
- 不要因为同属 OTU 或 `/v1/videos` 就复用所有参数
- 参数差异写进 stage config 或函数边界，不要散落在 dispatcher
- 真实 smoke test 前先用 mock 测请求形态，避免花钱后才发现字段错

## 22. 多参考图要先排优先级，再处理数量上限

2026-05-27 多模特支持暴露出一个典型问题：产品、多人类模特、宠物模特、环境图、故事板图都想传，但 API 参考图数量有限。后续实现里约束为：产品和所有选中模特优先，Omni 视频还要给故事板图预留一个 slot，超出必要上限时直接失败。

以后处理参考素材时：
- 明确必选参考和可选参考
- 必选参考超出 API 上限时 fail fast，不要静默裁掉角色或产品
- 视频阶段如果必须带故事板图，要先预留它的位置
- 多张产品图/多张模特图要约定取第几张；当前常用策略是每个模特取第一张照片
- 单测断言 reference role 顺序，而不是只断言数量

## 23. 模型输出结构不够完整时，要在入库前失败

2026-05-27 故事板 prompt validation 修过一轮：模型生成的 `image_prompt` 必须是可直接出图的完整提示词，包含顶部表头、中部素材/参考区、底部剧情分镜区；Storyboard 01 才能包含核心冲突和黄金 3 秒钩子，Storyboard 02 以后不能再出现这些字段。

以后所有“模型拆分 -> 子记录入库 -> 后续烧图/烧视频”的链路都要：
- 在入库前校验最小完整性，不要把半成品 prompt 写进表里
- 对第 1 段和后续段做不同校验，避免首段规则污染所有分段
- 同时支持中文和英文 marker，因为 prompt 真源可能混合语言
- 错误要指明第几段缺了什么或多了什么

## 24. 配置 bootstrap 不能因为某个 API Key 缺失就跳过纯 prompt 配置

2026-05-27 的故事板配置 bootstrap 后来补了一个约束：`故事板图片提示词拆分` 这类纯 prompt 配置记录，不应该依赖 OTU 图片/视频 API Key 才能创建。否则缺少某个模型密钥会连 prompt 真源都补不出来。

以后 bootstrap 配置时：
- 按环节拆分依赖，文本拆分、图片生成、视频生成分别检查各自需要的字段
- 纯 prompt 记录不要写入 `API Key`
- 打印日志不得泄漏环境变量里的 key
- 单测覆盖“没有图片/视频 key 时仍能创建 prompt 配置”

## 25. 旧字段改名要迁移，不要并存两个近义字段

2026-05-27 首尾帧表把 `批量拆分状态` 收口为 `拆分状态`，同时测试迁移逻辑，避免线上表里出现两个近义状态字段。

以后字段命名收口时：
- 优先迁移/重命名旧字段，而不是新建一个相似字段
- 迁移脚本要检查目标字段是否已存在，避免重复创建
- healthcheck 和 dispatcher 要同步改成新字段名
- 文档里只保留新口径，旧名只在迁移说明里出现

## 26. 附件文档和媒体附件不要用同一个下载函数

2026-05-27 首尾帧文档解析测试明确：`首尾帧文档附件` 作为文本/Markdown 源文档时，要走 raw attachment download，而不是图片/视频媒体下载逻辑。

以后读取飞书附件时：
- 文档源文件走 raw download，并按文本解码
- 图片/视频参考图走 media download
- 不要通过文件名猜类型后混用下载函数
- 单测要断言文档解析路径没有调用图片媒体下载函数

## 27. 同一张生产表混合多类记录时，用户视图必须按类型和状态收口

2026-06-01 多角色首尾帧表把母任务、参考图、关键帧、视频片段和废弃记录都放在 `001-多角色首尾帧生成表` 里。最初所有记录混在一个 `Grid View`，用户审核时很难判断哪条该看、哪条只是系统子记录。

以后这类单表多记录类型链路默认要：
- 保留一个 `99-全字段系统视图` 给排错，不把它作为用户入口
- 用户入口按流程拆成 `01-*`、`02-*`、`03-*`、`04-*` 等视图
- 每个用户视图同时筛 `记录类型` 和 `记录状态=有效`
- 失败和废弃记录单独放到 `98-*`、`00-*`
- 表结构脚本要能把默认 `Grid View` 重命名并补齐过滤条件，避免新建表后重新变乱

## 28. 人物参考图风格要在 prompt 真源收口，不在 worker 二次拼接

2026-06-01 多角色人物参考图生成链路确认：解析模型输出 `assets[].prompt`，子记录原样写入 `参考提示词`，`render_reference_image()` 直接把这个提示词送文生图。worker 不额外追加人物风格，这是为了避免 prompt 真源分裂。

以后调整人物参考图风格时：
- 同步改代码 fallback `DEFAULT_PARSE_PROMPT` 和飞书配置表 `环节=多角色首尾帧解析-Gemini` 的 `提示词`
- human 资产 prompt 必须约束 `single person`、`one angle`、`front-facing`、`full face visible`
- 明确禁止 `no side profile`、遮脸、背影、多视角、角色设定表、contact sheet、turnaround
- 明确要求 `UGC smartphone photo`、自然光、日常衣着、本地素人感、`natural skin texture`
- 不在图片 worker 里二次拼接风格；已有旧参考图不会自动重跑，需要重新拆解或重新生成

## 29. Dispatcher 并发配置以飞书表为日常入口

2026-06-05 起，dispatcher 并发控制应优先通过 `初始化-模型与API配置` 管理：运行环节记录用 `环节最大并发` 控制单环节并发，`Dispatcher并发控制` 路由开关记录用 `全局最大并发` 控制总并发。`环节最大并发=0` 表示暂停该环节，空值表示沿用本地默认；不要为了临时调并发再直接改 `tk_dispatcher.py`。
